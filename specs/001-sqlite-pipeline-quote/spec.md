# Feature Specification: 地端 SQLite 多階段 PDF 報價單處理系統

**Feature Branch**: `001-sqlite-pipeline-quote`
**Created**: 2026-01-07
**Status**: Draft
**Input**: 建立可地端運行的自動化家具報價單系統，使用輕量級 LLM 在受限 Context Window 下穩定處理

## User Scenarios & Testing *(mandatory)*

### User Story 1 - PDF 上傳與報價單產出 (Priority: P1)

使用者上傳多份供應商 PDF（家具規格書、數量總表、面料表、Index），系統自動解析並產出符合惠而蒙 (Fairmont) 格式的 15 欄位 Excel 報價單，包含嵌入的家具圖片。

**Why this priority**: 這是系統的核心價值，沒有這個功能，整個系統沒有意義。

**Independent Test**: 上傳一組完整的供應商 PDF，驗證產出的 Excel 包含正確的 15 個欄位、正確的數量合併結果、以及嵌入的家具圖片。

**Acceptance Scenarios**:

1. **Given** 使用者已準備供應商 PDF 檔案（含數量總表和明細規格表），**When** 使用者上傳這些 PDF，**Then** 系統產出包含 15 欄位的 Excel 檔案
2. **Given** PDF 中包含家具圖片，**When** 系統處理完成，**Then** Excel 中嵌入去重後的最佳解析度圖片
3. **Given** 數量總表與明細規格表中 Qty 數值不同，**When** 系統合併資料，**Then** 以數量總表的 Qty 為準
4. **Given** Index 檔案包含 Location 資訊，**When** 系統處理完成，**Then** Excel 中正確顯示家具位置

---

### User Story 2 - 斷點續傳與失敗恢復 (Priority: P2)

當處理過程中發生中斷（如 OOM、斷電），使用者重啟系統後能從最後完成的階段繼續處理，而非從頭開始，避免重複消耗運算資源。

**Why this priority**: 地端環境資源有限，失敗恢復能力是系統可用性的關鍵保障。

**Independent Test**: 在處理中途手動終止程序，重啟後驗證系統能識別已完成的階段並從斷點繼續。

**Acceptance Scenarios**:

1. **Given** 系統正在處理第 4 階段時中斷，**When** 使用者重新啟動系統，**Then** 系統從第 4 階段繼續而非重新開始
2. **Given** 某個階段處理失敗，**When** 使用者查看進度，**Then** 系統顯示失敗的具體階段與錯誤訊息
3. **Given** 部分資料已成功處理並儲存，**When** 系統恢復後重試，**Then** 已成功的資料不會重新處理

---

### User Story 3 - 快取機制與重複檔案處理 (Priority: P3)

使用者上傳相同的 PDF 檔案時，系統能識別並直接返回先前的處理結果，實現秒級回應，避免重複消耗 LLM 運算資源。

**Why this priority**: 快取機制能大幅減少資源消耗，提升使用者體驗，但不影響核心功能。

**Independent Test**: 上傳相同 Hash 的 PDF 兩次，第二次應在數秒內返回結果。

**Acceptance Scenarios**:

1. **Given** 使用者曾上傳某 PDF 並成功處理，**When** 使用者再次上傳相同檔案，**Then** 系統在 3 秒內返回快取結果
2. **Given** 快取中存在處理結果，**When** 系統返回快取，**Then** 結果與原始處理完全一致

---

### User Story 4 - 處理進度即時回報 (Priority: P4)

使用者能在前端介面看到目前處理進度，包含當前階段、階段進度百分比，以便了解預計完成時間。

**Why this priority**: 提升使用者體驗，但不影響核心處理功能。

**Independent Test**: 呼叫進度 API，驗證返回當前階段編號、總階段數、以及百分比進度。

**Acceptance Scenarios**:

1. **Given** 系統正在處理 PDF，**When** 前端呼叫進度 API，**Then** 返回格式如「階段 4/7：項目詳細擷取中... 35%」
2. **Given** 處理完成，**When** 前端呼叫進度 API，**Then** 返回完成狀態與結果檔案路徑

---

### User Story 5 - 架構切換與回退 (Priority: P5)

管理員能透過環境變數在新舊處理架構間切換，確保新架構出問題時能快速回退。

**Why this priority**: 部署彈性，降低升級風險。

**Independent Test**: 修改環境變數後重啟，驗證系統使用對應的處理架構。

**Acceptance Scenarios**:

1. **Given** 環境變數 `USE_SQLITE_PIPELINE=true`，**When** 系統啟動，**Then** 使用新的 SQLite 多階段管線
2. **Given** 環境變數 `USE_SQLITE_PIPELINE=false`，**When** 系統啟動，**Then** 使用舊有處理架構

---

### Edge Cases

- 當上傳的 PDF 無法解析或格式損壞時，系統應返回明確的繁體中文錯誤訊息
- 當 PDF 中缺少必要資訊（如無 Item No.）時，系統應標記該項目並繼續處理其他項目
- 當同時上傳多個檔案時，系統應透過佇列機制依序或並行處理
- 當 LLM 回應超過預期 Token 限制時，系統應採用分塊策略重試
- 當資料庫檔案損壞或無法存取時，系統應提供清晰的錯誤訊息與恢復建議
- 當 Item No. 格式不一致時（如 `DLX-201 .1` vs `DLX-201.1`），系統應自動正規化後再合併
- 當同一項目在不同 PDF 使用不同編號時（如數量總表 `DLX-1010` vs 規格書 `DLX-100`），系統應嘗試透過 Description 智慧匹配或標記為待人工確認
- 當面料項目 (500 系列) 缺少對應家具項目時，系統應獨立列出面料資訊
- 當家具規格書包含多種圖片類型（家具圖、面料圖、工程圖）時，系統應優先選擇家具實物圖嵌入 Excel

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統必須支援上傳多份 PDF 檔案（家具規格書、數量總表、面料表、Index）
- **FR-002**: 系統必須自動識別 PDF 的角色類型（數量總表 vs 明細規格表）
- **FR-003**: 系統必須以 Item No. 為鍵值合併來自不同 PDF 的資料
- **FR-004**: 系統必須產出符合 15 欄位規範的 Excel 報價單
- **FR-005**: 系統必須自動擷取 PDF 中的家具圖片，並去重選擇最佳解析度版本嵌入 Excel
- **FR-006**: 當數量總表與明細規格表的 Qty 數值衝突時，系統必須以數量總表為準
- **FR-007**: 系統必須將每個處理階段的中間結果持久化至本地資料庫
- **FR-008**: 系統必須支援從最後完成的階段恢復處理（斷點續傳）
- **FR-009**: 系統必須對相同 Hash 的檔案返回快取結果
- **FR-010**: 系統必須控制單次 LLM 呼叫的 Prompt 在 2K tokens 以內
- **FR-011**: 系統必須提供進度查詢 API，返回當前階段與進度百分比
- **FR-012**: 系統必須支援透過環境變數切換處理架構
- **FR-013**: 系統必須支援多個批次的佇列處理，依序執行，一次只處理一個批次
- **FR-014**: 系統必須以繁體中文顯示所有使用者面向的訊息與錯誤
- **FR-015**: 系統必須正規化 Item No. 格式（移除多餘空格、統一破折號位置）後再進行合併
- **FR-016**: 系統必須處理面料項目 (500 系列) 與家具項目的關聯，透過 FURNITURE COM 欄位建立對應關係
- **FR-017**: 系統必須支援 Item No. 智慧匹配，當編號不完全一致時嘗試以 Description 輔助配對
- **FR-018**: 系統必須區分並標記圖片類型（家具實物圖、面料樣本圖、工程圖），優先嵌入家具實物圖
- **FR-019**: 系統必須記錄每個處理階段的開始時間、完成時間與錯誤訊息（階段層級日誌）
- **FR-020**: 當 LLM 呼叫失敗時，系統必須以指數退避策略重試最多 3 次，超過後標記該項目為失敗
- **FR-021**: 系統必須自動清除超過 1 天的快取記錄（POC 階段設定）

### Key Entities

- **處理批次 (ProcessingBatch)**: 代表一次 PDF 上傳處理請求，包含批次 ID、狀態、建立時間、完成時間
- **上傳檔案 (UploadedFile)**: 代表單一上傳的 PDF，包含檔案 Hash、檔案類型（角色）、原始檔名、關聯批次
- **處理階段 (ProcessingStage)**: 代表處理管線中的一個階段，包含階段編號、狀態、進度百分比、開始/結束時間
- **家具項目 (FurnitureItem)**: 代表解析出的單一家具，包含 Item No.、描述、尺寸、材質、數量、位置、圖片路徑、關聯面料項目列表
- **面料項目 (FabricItem)**: 代表解析出的面料/皮革 (500 系列)，包含 Item No.、品牌 (Brand)、花紋 (Pattern)、顏色、寬度、材質成分 (Content)、耐磨度 (Abrasion)、供應商 (Vendor)、關聯家具項目 (FURNITURE COM)
- **快取記錄 (CacheRecord)**: 代表已處理檔案的快取，包含檔案 Hash、處理結果路徑、建立時間

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 使用者上傳完整 PDF 後，系統在 15 分鐘內完成處理並產出 Excel（單一批次 100 項目內）
- **SC-002**: 系統處理過程中不因 Context Window 限制而崩潰
- **SC-003**: 重複上傳相同檔案時，系統在 3 秒內返回快取結果
- **SC-004**: 系統中斷後恢復，能從斷點繼續而非從頭開始
- **SC-005**: 95% 以上的家具項目能正確合併數量總表與明細規格表的資料
- **SC-006**: 所有錯誤訊息以繁體中文顯示，使用者能理解問題所在
- **SC-007**: 進度 API 每秒至少更新一次當前狀態
- **SC-008**: 系統支援 10 個以上併發上傳請求的排隊處理

## Clarifications

### Session 2026-01-07

- Q: 此系統是否需要使用者認證機制？ → A: 無需認證 - 地端單機環境，信任所有存取者
- Q: 系統需要什麼程度的日誌記錄機制？ → A: 階段層級 - 記錄每個處理階段的開始、完成、錯誤
- Q: 當 LLM API 呼叫失敗或逾時時，系統應如何處理？ → A: 重試 3 次 - 指數退避重試，超過後標記失敗
- Q: 當多個使用者同時上傳 PDF 時，系統應如何處理？ → A: 佇列處理 - 依序處理，一次只執行一個批次
- Q: 快取的處理結果應保留多久？ → A: 1 天（POC 階段）

## Assumptions

- 系統部署於受信任的地端內網環境，無需使用者認證機制
- 使用者上傳的 PDF 為標準格式，可被 PDF 解析工具讀取
- 地端環境已安裝並配置好 Gemma-3-12b 或相容的 LLM
- 家具 Item No. 在同一批次的 PDF 中是唯一且一致的識別碼（允許格式差異，系統會正規化處理）
- 資料庫檔案位於 `data/fairmont.db`，系統有讀寫權限
- PDF 類型識別基於檔案內容結構：數量總表含 CODE/TOTAL QTY 欄位、Index 含 Room/Location 欄位、規格書含詳細尺寸與圖片
- 15 欄位規範（惠而蒙 Fairmont 格式）：
  - **核心解析欄位（由 AI 提取）**：
    1. NO. - 序號
    2. Item No. - 項目編號（如 DLX-100）
    3. Description - 品名描述（如 Bedside Table）
    4. Photo - 產品圖片（系統自動截圖並嵌入儲存格）
    5. Dimension (mm) - 家具：尺寸 (寬 x 深 x 高)；面料：Fairmont 預定格式
    6. Qty - 家具：數量（從數量總表獲取）；面料：留空
    7. UOM - 單位（如 ea, m）
    8. Materials Used / Specs - 材料詳細規格（AI 擷取的材質細節）
    9. Location - 家具：房型；面料：所屬家具
    10. Note - 來源不明確先留空
    11. Brand - 品牌/供應商（由 AI 從規格書獲取）
  - **預留與對接欄位（預設空白或公式，供客戶手動填寫）**：
    12. Unit Rate - 單價（預留欄位，通常由採購填寫）
    13. Amount - 總價（預留欄位，通常包含公式 Qty × Unit Rate）
    14. CBM (m³) - 材積（預留欄位）
    15. Total CBM - 總材積（預留欄位）
